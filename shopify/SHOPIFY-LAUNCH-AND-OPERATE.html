Launch + operate — Shopify post-submission ops

Everything beyond the initial App Store submission: annual BFS reviews, the full Protected Customer Data requirements, Managed Pricing setup, billing patterns, deployment, app distribution, sunsetting, ad campaigns, and marketing. Companion to the submission checklist + Claude actions docs.

Two gaps to close right away

1. Confirm app.billing.tsx uses Managed App Pricing (or `appSubscriptionCreate`). We never explicitly verified this. If it rolls its own (e.g. Stripe), the app will be rejected on review for failing req 1.2.1. Likely a 30-minute audit + small refactor.

2. PCD L1.6 — opt-out for automated decisions. Our size recommendation IS automated decision-making. Required: either a "request manual review" pathway in the SDK, or an explicit privacy-policy clause + a UI disclosure on the try-on widget. Without it, we will fail the data protection review.

01 Built for Shopify — annual reviews

Once we earn BFS, Shopify re-reviews us every year to confirm we still meet the criteria. Knowing the cycle lets us prep before the email arrives.

StageDetail
WhenAbout 1 year from initial BFS approval, around the same time each year
How we hearEmail + Partner Dashboard banner
DurationA few days to ~1 week (queue + actual review)
Result deliveryEmail with verdict + reasons
PassNo action — certified for another year
Fail60-day grace period to fix issues. App keeps BFS during the grace.
Miss the graceBFS removed. Can re-apply any time.

Pre-review prep (run once a year)

  1. Re-run the full submission checklist on the current state of the app.
  2. Re-run Lighthouse on Dawn dev store with our block; confirm ≤ −10 pts impact.
  3. Confirm Web Vitals targets in Partner Dashboard (LCP ≤ 2.5s, CLS ≤ 0.1, INP ≤ 200ms @ p75).
  4. Confirm install / review / rating thresholds still met.
  5. Re-grep for REST `.json` calls (Shopify keeps tightening this).

02 Regain lost BFS status

BFS can be lost between reviews if automated criteria slip. Auto-loss is recoverable on its own once you're back in compliance — no resubmission needed.

Automated criteria (lose after 60 days of failure)

  • Uninstalls cleanly (theme app extensions properly remove)
  • App is embedded in Shopify admin
  • Minimizes impact on checkout speed
  • Admin performance — meets 75th-percentile Web Vitals targets
  • Minimum number of installs
  • Minimum number of reviews
  • Minimum app rating

Track these in real time on Partner Dashboard → Apps → Distribution.

Manual criteria (ongoing)

Apps may be reviewed at any time for manually-checked items (design, integration). 60 days to fix if anything fails. Same grace logic as annual review.

Auto-regain

BFS is restored automatically when all criteria pass again. No reapplication needed. Shopify might still spot-check after auto-restore.

03 Protected Customer Data — full L1+L2 requirements

If you handle any protected fields (we do — order webhooks include customer email/name/address), you must implement all 9 L1 + 7 L2 requirements. Shopify checks these in the data protection review.

Level 1 (always required if touching protected fields)

#RequirementHow we'd evidence it
L1.1Process the minimum personal data neededStrip customer.email, customer.firstName, address from order webhooks unless explicitly approved + needed. Code-level audit.
L1.2Inform merchants what you process + whyPrivacy policy section + DPA clause naming each field.
L1.3Limit processing to stated purposesDocument each field's purpose. Don't reuse data across products.
L1.4Honor customer consentIf buyer rejects cookies, fall back gracefully (anonymous session). Add CMP integration.
L1.5Honor "Do Not Sell" / opt-outAPI endpoint + privacy form for individual opt-outs.
L1.6Allow opt-out of automated decisions with legal/significant effectOur size recommendation IS automated. Need either a "request manual review" pathway, or explicit privacy-policy disclosure + a UI consent step on the try-on widget.
L1.7Have a DPA with merchantsSign a DPA on installation flow (click-through), attached to ToS.
L1.8Apply retention periods + enforceCron jobs to delete: photo bytes (immediate), sizing profiles (12 mo), analytics events (24 mo).
L1.9Encrypt at rest + in transitTLS everywhere ✓. Mongo Atlas encryption-at-rest must be ON. Document.

Level 2 (required if you touch name/address/phone/email)

#RequirementHow we'd evidence it
L2.1Encrypt backupsMongo Atlas backups are encrypted by default — confirm in cluster settings + screenshot.
L2.2Test ↔ prod separationSeparate clusters / databases. No prod data in dev. Document and enforce via env vars.
L2.3Have a DLP strategy1-page document covering backups, encryption, access control, key rotation, secrets management.
L2.4Limit staff accessAtlas IAM — revoke unused accounts; least-privilege roles.
L2.5Strong staff passwordsPassword policy + MFA mandatory across Atlas, Cloudinary, Shopify Partners, GitHub.
L2.6Access log to PCDAtlas audit logs ON. Review monthly. Retain ≥ 90 days.
L2.7Security incident response policy1-page doc: severity scale, roles, escalation, evidence collection, merchant + Shopify notification thresholds.
Heads-up: Shopify can request evidence for ALL of these during a data protection review — not just attestations. Have screenshots, configs, and policy docs filed somewhere you can pull on demand.

04 Data Protection Review — what triggers it + how to prep

Shopify can select any app that handles PCD for a deep review. We're more likely to be selected once we cross install thresholds.

Selection signals

Apps are more likely to be reviewed if they have:

  • High number of merchant installs
  • High volume of customer records
  • More protected customer fields approved
  • Long retention of personal data

How to prep (do this before submission, file the artifacts)

  1. Privacy policy + DPA published and linked from listing
  2. Per-field PCD justification text saved in the Partner Dashboard submission
  3. Atlas IAM screenshots (least-privilege)
  4. Atlas encryption-at-rest screenshot
  5. Atlas audit-log enabled screenshot
  6. Backup encryption settings screenshot
  7. Retention cron job source + schedule
  8. 1-page DLP doc
  9. 1-page incident response policy
  10. Sub-processor list with signed DPAs (Cloudinary, Google Cloud, Atlas)
  11. Buyer opt-out endpoint + privacy form (for L1.5)
  12. Manual-review pathway for the try-on widget (for L1.6)

If selected: Shopify emails instructions. They want evidence, not just claims. Respond within whatever window they give (usually 2-4 weeks).

05 Billing & Managed App Pricing

Apps on the App Store must use Shopify's billing API (Managed Pricing or programmatic via appSubscriptionCreate). No Stripe. No direct credit cards.

Managed App Pricing (the easier path)

Shopify hosts a plan-selection page; you configure plans in the Partner Dashboard. Pros: less code, automatic test-charges on dev stores, automatic plan-change UX, automatic webhook events.

Setup

  1. Partner Dashboard → App → Distribution → Pricing → enable Managed Pricing
  2. Define plans: name, price, interval (every 30 days, annually), free trial length, included features
  3. Generate the plan-selection welcome link (one per plan or shared)
  4. In your app, redirect un-subscribed merchants to the welcome link
  5. Subscribe to billing webhooks: app_subscriptions/update, app/uninstalled

Public vs private plans

TypeUse case
PublicVisible to all merchants. Most plans.
PrivateHidden from the catalog — only accessible via direct link. Use for custom/enterprise deals or beta-tester pricing.

Welcome links

Direct links to the plan-selection page or a specific plan. Useful for onboarding emails, marketing pages, or in-app upgrade buttons.

Proration

When a merchant changes plans, Shopify prorates the price difference automatically. Upgrades are charged immediately. Downgrades take effect next cycle.

Test charges

On dev stores, charges are always test charges — no real money. You can iterate freely.

Programmatic billing (more control)

Use appSubscriptionCreate via the Admin GraphQL API. Use this if you need: usage-based pricing not supported by Managed, custom proration, complex plan combinations, or per-store pricing.

Required mutations

  • appSubscriptionCreate — start a subscription
  • appSubscriptionCancel — cancel
  • appUsageRecordCreate — log usage for usage-based plans
  • appSubscriptionLineItemUpdate — change a plan's max charge

06 Subscription patterns

Time-based subscription

Flat fee per cycle (every 30 days or annually). Simplest model.

Examples: $29 / month. Good for: most SaaS apps including ours.

Usage-based subscription

Per-event pricing. You log a usage charge each time the merchant uses a paid feature. Each charge is capped by a `cappedAmount` on the line item; once hit, no more charges that cycle.

Examples: $0.05 per try-on, capped at $50/month. Good for: pay-as-you-go tiers.

// Log usage
appUsageRecordCreate(
  description: "Try-on rendered",
  price: { amount: 0.05, currencyCode: USD },
  subscriptionLineItemId: "..."
)

Combined time + usage

Base fee plus usage tier. Created as ONE subscription with TWO line items. Common for "enterprise" plans.

Examples: $99/mo base + $0.02 per try-on after 1000.

Complex pricing models

Tiered, volume discounts, region-specific, plan downgrades — Shopify documents specific patterns. Generally: each tier = a separate plan. Migrate merchants between plans on usage thresholds via appSubscriptionCancel + new appSubscriptionCreate.

Update max charge

If a merchant approaches their `cappedAmount` and wants to keep going, you must request a new approval via appSubscriptionLineItemUpdate. Merchant gets a Shopify-hosted approval page.

07 App credits, one-time charges & refunds

One-time purchases

Use appPurchaseOneTimeCreate for non-recurring items (e.g. an add-on pack, a one-time setup fee). Merchant approves once, charged once.

App credits

Issue a credit to a merchant's next invoice using appCredit. Common cases:

  • Refund part of a charge (Shopify doesn't process direct refunds — credits are the mechanism)
  • Promotional credit ("$10 off your next month")
  • SLA / outage compensation

Limits: credit cannot exceed the amount the merchant has paid you in the last 30 days. Credits reduce your earnings (negative entry).

Refund app charges

True refunds (money back to the card) require Shopify support — not API. For most cases, App Credits are the equivalent.

View charges & earnings

Two surfaces:

  • Partner Dashboard → Apps → app → Overview / Insights / App history (visual, exportable to CSV)
  • Partner GraphQL API — programmatic access to transactions, shopifyPaymentsBalance, app(id) usage. Useful for custom revenue dashboards on our side.

08 Deployment

Shopify documents a few sanctioned deployment paths. We're on a DigitalOcean droplet with PM2 — that's fine, but here are the alternatives + what they buy us.

Hosting options

OptionWhat it buysTrade-off
DigitalOcean / VPS + PM2 (us today)Cheap, full controlYou manage scaling + uptime
Google Cloud Run (Shopify-documented)Auto-scale, no server mgmt, integrates with their ad/perf monitoringCold starts, more $ at high traffic
Vercel / Netlify / RenderZero-config CI/CD, edge networkRR7 deployment is solid; budget creep at scale
Fly.io / RailwayMulti-region, Postgres/Redis bundled, easy CINewer, fewer Shopify-side guides

App versions

Shopify tracks every deploy of your app/extension as a version. Versions are how Shopify rolls out scope changes, theme extension code, and webhook subscriptions to merchants.

Key commands:

shopify app deploy           # Push current code as a new version
shopify app versions list    # List deployed versions
shopify app versions release # Activate a specific version

CD pipeline

For a multi-piece app like ours (admin + theme extension + backend), the pipeline shape:

  1. Push to main → CI runs tests
  2. If green: build admin → push to droplet, restart PM2
  3. Build theme extension → shopify app deploy (creates a new version)
  4. Activate the new version automatically OR via manual approval (recommended for theme extension changes — they ship to all merchants)
  5. Backend deploys independently to droplet

Every merchant on the previous version stays on it until they manually update OR the new version is released as the default.

09 Distribution & visibility

Fully visible vs limited visibility

ModeWhere the listing appearsWhen to use
Fully visibleApp Store search, category pages, Google. Default.You want broad reach.
Limited visibilityOnly via direct link. NOT indexed.Soft launch / private beta / curated rollout.

Both modes still allow merchants to install via the direct App Store URL. Toggle in Partner Dashboard → Apps → Distribution.

Recommended launch plan

  1. Submit, get approved with limited visibility
  2. Onboard 5-10 friendly merchants via direct link to validate end-to-end
  3. Collect first reviews
  4. Switch to fully visible
  5. Run App Store ads (see §15) to seed install velocity

10 Sunsetting an app

If we ever wind the app down, Shopify has a documented graceful path — required to stay in good standing.

  1. Notify all installed merchants ≥ 30 days in advance via in-app banner + email
  2. Give them an export path for any data we hold
  3. Stop new installs (limited visibility)
  4. Honor billing cancellations promptly
  5. On D-day: stop accepting webhooks; reply 410 Gone to API hits
  6. Run the shop/redact handler on every shop after the 48h Shopify grace
  7. Remove the listing from Partner Dashboard

13 Revenue share rules

Shopify's cut of our revenue depends on per-app earnings tier. Worth knowing before pricing decisions.

  • Up to a defined annual revenue threshold per partner: 0% Shopify cut (you keep ~100% minus standard payment processing).
  • Above the threshold: standard split (currently 15% Shopify cut for most apps, but verify the current rate in the Partner Dashboard — Shopify changes this periodically).
  • Built for Shopify status doesn't change the rev share — it's about visibility + promotion.

Practical impact: early-stage apps usually pay nothing to Shopify on the first chunk of revenue. Don't over-engineer the rev-share math into pricing — Shopify deducts at payout time.

14 App Store ads

Paid placement in App Store search results. Bidding model. Run after launch + first reviews are in.

How it works

  1. You bid on keywords merchants might search ("size chart", "virtual try on", "fashion fit", etc.)
  2. Your ad shows above organic results when a merchant searches
  3. You pay per click (CPC), not per impression
  4. Shopify takes a small fee on top of the CPC

Setup checklist

  1. App is fully visible (not limited)
  2. App listing complete + reviewed by Shopify
  3. Set ad permissions (who in your team can manage)
  4. Add a payment method for ad billing
  5. Create your first ad campaign with target keywords + max bid
  6. Track performance via the ads dashboard (impressions, clicks, installs, ROI)

Ad billing

Charged separately from app earnings — ads are an expense, not a revenue offset. Invoice from Shopify monthly.

Ad permissions

Roles: ad admins (create / pause / delete) and ad viewers (read-only). Set in Partner Dashboard → team settings.

Recommended for us

  • Wait until: ≥ 5 reviews, BFS submitted (not yet approved is fine), at least one strong testimonial in listing copy
  • First campaign: ~$200–$500 budget, narrow keywords (avoid generic "shopify app")
  • Iterate weekly based on CTR + install conversion

15 Marketing & launch

Launch press release

Shopify provides a template + distribution guidance. Key elements:

  • What problem does it solve (1 line)
  • Concrete benefit ("install in 2 mins, no code")
  • Founder quote
  • App Store link
  • Brand assets attached (logo + screenshot)

Shopify brand assets

You can use Shopify's official "Available on the Shopify App Store" badge in your own marketing. Direct download from shopify.dev/docs/apps/launch/marketing/shopify-brand-assets. Rules:

  • Don't recolor the badge
  • Don't crop the Shopify glyph
  • Maintain padding around the badge
  • Link to your App Store listing

Track listing traffic

Append UTMs to App Store URLs from your marketing channels:

https://apps.shopify.com/your-app?utm_source=blog&utm_medium=referral&utm_campaign=q2_launch

Partner Dashboard → Apps → app → Distribution → "Listing traffic" tab shows referrers + UTM breakdown. Helps you double down on what's working.

Manage reviews

You can reply to every review in Partner Dashboard. Best practice: reply to every 1–3 star review with a constructive plan + a way to contact you. Shopify weighs response rate in BFS criteria.

Shopify quality checks

Outside annual reviews, Shopify runs automated quality checks on your app (uptime, install/uninstall ratios, refund rates, support response time). Failure here can trigger a manual review or temporary App Store de-listing. Stay above 95% uptime, < 5% same-day uninstalls.
